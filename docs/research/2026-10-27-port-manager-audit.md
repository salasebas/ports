# Ports audit and competitor inventory

Research date: October 27, 2026. Local baseline: `9d084f5021f20c61e641eb115d9846c37952122b`.

This is a read-only product and correctness audit. No application code, configuration, dependencies, or committed tests were changed. The report is the only repository addition. Disposable test programs and dependency caches were created under `/tmp`.

The review covers all eleven backend port modules, window and settings integration, folder actions, the Svelte stores, application routes, and product components. It does not audit every vendored shadcn primitive. Fourteen public competitor repositories were checked. Seven received an implementation-level comparison; the others received a first-party documentation and metadata comparison. This inventory is extensive within that scope, not a claim that every port manager or every possible defect has been found.

## Evidence and priority

- **R** means an isolated executable scenario reproduced the behavior using the actual project modules. IPC and Docker were replaced only at their external boundaries. The IPv6 scenario creates a real IPv6-only wildcard socket and verifies that IPv4 cannot reach it; its supplied LAN address is a test input.
- **C** means the current source confirms the described path and condition. That case was not independently reproduced in the desktop application.
- **Risk** means a plausible issue still needs a representative runtime test or profiling. Risks are not counted as confirmed findings.
- **P1** means a high-priority control or ownership defect. **P2** means a correctness, detection, resource, or concurrency defect. **P3** means a lower-priority persistence or diagnostic defect. No P0 finding was established.

There are **29 confirmed findings**, including **14 distinct findings reproduced by 15 temporary scenarios**. Five are P1, twenty-three are P2, and one is P3. Feature gaps and unconfirmed risks are counted separately.

## Confirmed control and ownership findings

### B01. P1, C. The selected process identity does not survive the UI-to-backend boundary

The action target contains only port, PID, and optional container ID. If an old row's PID is reused by a new process on the same port, `locate` accepts the new owner. `end` then captures the replacement's start time and treats that replacement as the intended target. The later start-time checks do not restore the original identity. History and health keys also omit process start identity.

Expected: a stale selection cannot stop or restart a replacement, including when the numeric PID is reused. Existing coverage rejects a different PID, not the same reused PID. See [IPC Target](/home/sebastian/projects/ports/src-tauri/src/ports/mod.rs:299), [locate](/home/sebastian/projects/ports/src-tauri/src/ports/control.rs:80), and [tracked history key](/home/sebastian/projects/ports/src-tauri/src/ports/sampler.rs:167). Portfox provides a useful comparison with [fresh identity checks against the selected snapshot](https://github.com/xergic/portfox/blob/87f7d283f41198d0633e447ad127bdddf8be6a90/Sources/PortfoxKit/Actions/ProcessController.swift).

### B02. P1, R. A prefork server can be displayed with a PID that Stop rejects

The sampler promotes a socket-owning worker to its same-executable master. Linux's `listeners` implementation can expose only a worker for the shared inode. Control requires the displayed PID itself to be in that socket-owner set. Its process refresh also omits executable paths, so it cannot apply the same master normalization.

A temporary real-process scenario created a Python master that closed its own socket after forking a worker. Sampling reported the master. Stop returned `is now used by python3` naming its own worker. The test cleaned up only its disposable process group.

Expected: sampling and control agree on service identity while preserving the actual listener identity. Existing prefork tests exercise `job` alone, not sampling through control. See [master normalization](/home/sebastian/projects/ports/src-tauri/src/ports/processes.rs:168), [reported PID](/home/sebastian/projects/ports/src-tauri/src/ports/sampler.rs:293), and [control validation](/home/sebastian/projects/ports/src-tauri/src/ports/control.rs:73).

### B03. P1, R. A protected or hidden server can be stopped through another row of its process or job

Protection is keyed by project folder or individual port. Cleanup eligibility is calculated per row. Stop acts on the whole selected process tree and sometimes its shell job group. Protecting port A of a process without a detected project leaves port B eligible; stopping B also closes A. Shared task runners spanning folders can cross project protection boundaries as well. A hidden sibling can be affected through the same mechanism.

The temporary store scenario protected one of two ports with the same PID. The second remained eligible for cleanup. Protection does correctly cover rows with the exact same project folder; the defect concerns different protection keys sharing a destructive scope.

Expected: the cleanup promise that protected servers remain running holds for the actual action scope. The confirmation should also identify affected sibling ports and services. See [protection key](/home/sebastian/projects/ports/src/lib/ports/ports-store.svelte.ts:42), [eligibility](/home/sebastian/projects/ports/src/lib/ports/ports-store.svelte.ts:139), [job expansion](/home/sebastian/projects/ports/src-tauri/src/ports/processes.rs:147), and [group signals](/home/sebastian/projects/ports/src-tauri/src/ports/control.rs:144).

### B04. P1, R. Cleanup confirmation uses stale activity and protection

Opening cleanup captures an array of eligible rows. Confirmation uses that array without checking the latest snapshot or preferences. A listed server can become active, protected, or hidden while the dialog stays open, yet still be stopped. A protection change from the other window is a realistic trigger.

Two temporary scenarios reproduced this independently: protection changed after opening, and status changed from idle to running after opening. Both still invoked `stop_server`.

Expected: confirmation revalidates current eligibility and target identity. Existing cleanup tests confirm immediately and never change state in between. See [captured cleanup list](/home/sebastian/projects/ports/src/lib/ports/ports-store.svelte.ts:307) and [confirmation](/home/sebastian/projects/ports/src/lib/ports/ports-store.svelte.ts:311).

### B05. P2, C. Children forked during shutdown can survive

`end` captures the target set once. After SIGTERM, a target can fork a child and then exit. Once the original targets are gone, the function returns immediately. Group escalation is also conditional on an original target remaining in that group. A newly forked child can therefore survive, even if the port has been released.

Expected: the promised server-tree shutdown accounts for children created during shutdown without signaling an unrelated reused group. Existing coverage creates children before the scan. See [captured targets](/home/sebastian/projects/ports/src-tauri/src/ports/control.rs:107), [early completion](/home/sebastian/projects/ports/src-tauri/src/ports/control.rs:123), and [group membership gate](/home/sebastian/projects/ports/src-tauri/src/ports/control.rs:145).

### B06. P2, C. Restart readiness accepts an unrelated listener

After relaunching, readiness succeeds when any process listens on the numeric port. If another process takes that port while the new child is alive but still not serving, Ports reports a successful restart of the wrong service.

Expected: the launched service owns the expected binding, with readiness distinguished from mere occupancy. Existing restart coverage has no competing binder. See [wait_until_listening](/home/sebastian/projects/ports/src-tauri/src/ports/control.rs:315).

### B07. P2, C. The final free-port check ignores known unowned listeners

`ensure_free` checks only `Sockets.listening`, although discovery separately tracks `Sockets.unowned`. Stop can claim the port is free while an uninspectable process still holds or has taken it. Restart can proceed into a known conflict.

Expected: either occupied category prevents a free-port claim. See [ensure_free](/home/sebastian/projects/ports/src-tauri/src/ports/control.rs:197) and [unowned socket records](/home/sebastian/projects/ports/src-tauri/src/ports/sockets.rs:14).

### B08. P2, C. Discovery failures can become false stop-success messages

Socket scan errors are logged and converted into an empty or partial socket result. Control treats a missing owned listener as an already-free port. When discovery fails and no fallback recovers that listener, Stop can return success without stopping the still-running server. The frontend then removes its row and announces a free port.

Expected: control distinguishes unavailable discovery from verified absence. See [scan error handling](/home/sebastian/projects/ports/src-tauri/src/ports/sockets.rs:31), [locate absent branch](/home/sebastian/projects/ports/src-tauri/src/ports/control.rs:69), and [success message](/home/sebastian/projects/ports/src/lib/ports/ports-store.svelte.ts:290).

### B09. P1, C. Numeric-port identity conflates independent owners and Docker bindings

Two unrelated servers can bind the same number on different addresses. Sockets are grouped by port; `job` chooses one tree; the sampler emits one row and attaches addresses from all of them. The second service disappears from rows and server usage.

Docker attribution also ignores the published host IP. A container publishing `127.0.0.2:3000` can override the native listener at `127.0.0.1:3000`. A user acting on the apparent native port can consequently stop the wrong container. Multiple runtime results on the same number use the first entry.

Expected: binding and owner identities remain distinct; intentional multi-binding aggregation occurs only for the same service. The test named `leaves_out_an_unrelated_process_on_the_same_port` protects the other process from the chosen job but never verifies that discovery represents it separately. See [socket key](/home/sebastian/projects/ports/src-tauri/src/ports/sockets.rs:12), [job selection](/home/sebastian/projects/ports/src-tauri/src/ports/processes.rs:137), [container override](/home/sebastian/projects/ports/src-tauri/src/ports/sampler.rs:162), and [published data model](/home/sebastian/projects/ports/src-tauri/src/ports/containers.rs:46).

There is **no confirmed continuously growing application heap leak** in this audit. History records are normally bounded by time, missing tracked servers are removed, and alert records expire. Restart's one waiting thread per live launched child is intentional lifecycle management, not sufficient evidence of a leak. ## Behaviors not to copy blindly

- Swift PortKiller's [scanner control](https://github.com/productdevbook/port-killer/blob/2209b0fded4f58b8498aaf855e218a2a2b08067f/platforms/macos/Sources/PortScanner.swift) waits about 500 ms before issuing SIGKILL. Its [deep action](https://github.com/productdevbook/port-killer/blob/2209b0fded4f58b8498aaf855e218a2a2b08067f/platforms/macos/Sources/AppState%2BPortOperations.swift) also targets established-connection PIDs. That can include clients. Neither behavior establishes safer ownership than Ports.
- Rust PortKiller's [listener verification](https://github.com/gupsammy/PortKiller/blob/master/src/process/ports.rs) uses `lsof -p` with network selectors without the [AND selector documented by lsof](https://lsof.readthedocs.io/en/stable/manpage/). Its function comments must not be treated as proof of exact selected-port identity. Its numeric-port Docker map and narrow default-port Homebrew matching are also limitations, not a universal integration model.
- Corvid's [scanner](https://github.com/CorvidLabs/Ports/blob/4254b6f2f9bea2f6fca923642b696de78180a4ac/Sources/PortViewer/Services/PortScanner.swift) drains its pipe in the process termination handler. Large output needs separate deadlock testing because a full pipe can block the child before exit. This is a source-level risk in the peer, not a reproduced defect in Ports.
- Portbar's inspected [external-process control](https://github.com/1fc0nfig/portbar/blob/007243866902338c3304eb04530f0fd7bd58b387/Sources/Portbar/System/ProcessControl.swift) does not establish the same captured-start-identity checks as Portfox. Its website and repository README also differ on updates; this report does not rely on the website's no-update claim.
- WhatThePort [issue #48](https://github.com/tomjohndesign/what-the-port/issues/48), opened October 21, reports transient build growth labeled as leaks and a Bazel listener labeled as Vite. That is a user report about version 2.5.1, not proof that the latest source still behaves identically. It does reinforce the local B14/B17 concerns. Its code should not be copied as evidence that a growth notification proves a memory leak.
